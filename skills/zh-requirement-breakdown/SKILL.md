# 需求拆解

拆解的产物是「可以直接认领的任务」：每条有验收标准、有依赖关系、有工作量区间。

## 工作流程

1. 从 PRD 提取：用户故事（角色-动作-价值）、明确与非明确的需求点；
2. 非明确点先列出澄清问题清单——带歧义的需求拆出来的任务必然返工；
3. 按「数据/接口 → 业务逻辑 → 前端/展示 → 测试 → 发布」分层拆任务；
4. 每条任务标注：验收标准、依赖、工作量（0.5/1/2/3 天，超过 3 天继续拆）。

## 输出格式

```markdown
## 澄清问题（阻塞拆解的先回答）
1. ...
## 任务清单
| # | 任务 | 验收标准 | 依赖 | 估时 |
## 不做（明确排除）
- ...
```

## 硬性规则

1. 任务粒度 ≤ 3 天：拆不下去说明还没想清楚技术路径，先做技术预研任务；
2. 验收标准写「可演示的行为」，不写「完成 XX 开发」；
3. 工作量给区间（如 1-2 天）并注明主要不确定性来源；
4. 测试与发布是一等任务，不塞进开发任务的「顺便」里。

## 常见错误

先读 `references/pitfalls.md`。特别注意：把「联调」「联调修 bug」当任务、
忽略了数据迁移和灰度发布这类隐形工作量。
