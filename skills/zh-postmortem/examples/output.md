# orders 下单失败事故复盘（2026-11-04）

## 事故概述

- 等级：P1（核心交易链路受损）
- 持续时间：20:12 - 20:33（21 分钟）
- 影响面：约 18% 下单请求失败，约 4200 单；无资金损失，无数据损坏。

## 时间线（UTC+8，只写已核实事实）

| 时间 | 事件 |
|---|---|
| 19:40 | 报表功能上线（含未加索引的统计查询） |
| 20:12 | orders 连接数达上限 500，下单开始失败；监控告警触发 |
| 20:14 | 值班工程师响应告警，开始排查 |
| 20:20 | 定位根因：报表慢查询全表扫描（单次约 30s）占满连接池 |
| 20:26 | 回滚报表功能，连接池逐步释放 |
| 20:33 | 下单完全恢复 |

## 根因分析

- 直接原因：新增报表查询未加索引，全表扫描单次约 30 秒，占满 orders 库连接池（上限 500），正常下单请求拿不到连接。
- 深层原因：统计类 SQL 不在既有上线评审清单范围内，绕过了慢查询审查环节。
- 系统缺陷：连接池没有按查询类型做并发隔离，单一慢查询即可耗尽全部连接。

## 经验教训

- "内部工具"的变更与对外变更走同一道门禁——绕过评审的统计查询是本次事故的入口。
- 连接池这类共享资源需要故障隔离设计，不能允许单类查询耗尽全部容量。
