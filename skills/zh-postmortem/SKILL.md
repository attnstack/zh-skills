# 故障复盘报告

复盘的目的不是追责，是让同一类事故不再发生第二次。产出物是「三个月后还能看懂」的行动文档。

## 工作流程

1. 收集四类素材：时间线材料（监控告警记录/聊天记录/操作日志）、影响面数据（失败率/单量/用户数）、处置动作、背景信息（近期变更）；
2. 按「先止血后复盘」确认事故已恢复，再动笔；
3. 按下方模板生成复盘；时间线只写可核实事实，推测与事实严格分离；
4. 根因分析沿「直接原因 → 深层原因 → 流程或系统缺陷」三层挖，停在人为失误等于没挖；
5. 用本 skill 的校验脚本自检：`node scripts/check.mjs < 复盘.md`，exit 0 才交付。

## 输出模板

```markdown
# <事故名称> 复盘报告（<日期>）

## 事故概述
等级 / 持续时间 / 影响面（量化：失败率、单量、用户数、资金）

## 时间线
时间精确到分钟并标注时区；每行一个事件，只写已核实事实。

## 根因分析
直接原因（技术上发生了什么）→ 深层原因（为什么会发生：流程/评审/监控缺口）→ 系统缺陷（架构上如何让事故扩大）。

## 行动项
每条必须有 Owner、期限、验证方式；按「防复发 > 缩短恢复时间 > 降低影响面」排序。

## 经验教训
不超过 3 条，写给未来的自己而不是写给领导。
```

## 硬性规则

1. 时间线混写推测是大忌——推测句必须带「推测」标注并给出验证路径；
2. 根因不允许停在「某某操作失误」：人只是流程的执行者，挖到流程或系统缺陷为止；
3. 每个行动项可跟踪：「加强意识」「多加测试」这类没有验证方式的条目不许出现；
4. 影响面必须量化，估算值标注口径；无资金损失也要写明「无资金损失」；
5. 措辞对事不对人：不出现具体个人的责任判定，只描述动作与流程。

## 常见错误

先读 `references/pitfalls.md`。特别注意：复盘写成检讨书、时间线用相对时间
（「大概几分钟后」）、根因分析只有一层就直接跳到行动项。
