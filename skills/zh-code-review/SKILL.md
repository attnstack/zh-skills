# 中文代码评审

评审的目标是「这次变更可以放心合入吗」，不是展示 reviewer 水平。

## 工作流程

1. 先看变更意图（PR 描述/commit message），再看 diff——不知道意图的评审一半是误报；
2. 按四层扫：正确性（逻辑/边界）→ 安全 → 可维护性（命名/重复/耦合）→ 风格；
3. 每条意见按下方分级标注，**P0 必须阻塞合入**；
4. 风格问题（与本次变更无关的历史问题）不提，或集中放「顺带说明」。

## 意见分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 会出错：逻辑错误、数据丢失、安全漏洞、并发问题 | 必须改完才能合 |
| P1 | 大概率出事：缺错误处理、资源泄漏、含糊的边界 | 合入前应改 |
| P2 | 可维护性：命名、重复代码、可测性 | 建议改，可延后 |
| nit | 风格偏好 | 随手改或不改 |

## 意见格式

每条：`[P?] 文件:行号` + 问题 + **为什么是问题** + 建议改法（给代码级建议，不写「建议优化」）。

```markdown
[P1] src/handler.ts:42 — 循环内逐条 await 查询
为什么：N+1，列表页 100 行会打 100 次库，高峰期拖垮连接池。
建议：改 IN 批量查询，或对 userId 集合做一次 join。
```

## 硬性规则

1. 不确定的问题要标注「不确定」，给出验证方法，不装确定；
2. 每条 P0/P1 必须附复现或触发条件，说不清触发条件就降级为 P2；
3. 表扬有价值的写法（一行「这里处理得好」比十条 nit 更能对齐标准）；
4. 评审范围是 diff，不是整个代码库。

先读 `references/pitfalls.md`。特别注意：只看代码不看调用方、
把「我会这么写」当问题提。
