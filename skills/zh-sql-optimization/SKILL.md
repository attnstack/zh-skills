# 慢 SQL 优化

优化建议必须挂在证据上：没有 EXPLAIN 输出，只给「经验直觉」并标注置信度。

## 工作流程

1. 拿三样东西：完整 SQL、表结构（含现有索引）、`EXPLAIN [ANALYZE]` 输出；缺哪个先要哪个；
2. 按「扫描方式 → JOIN 顺序 → 排序/临时表 → 返回行数」的顺序找最大开销点；
3. 每条建议给出：预期改善路径（执行计划里哪一项会变化）+ 验证方式；
4. 改写优先于加索引：先问「这个查询真的需要这些列/这些行吗」。

## 分析要点

| 症状（EXPLAIN 关键词） | 常见根因 | 处理方向 |
|---|---|---|
| type=ALL（全表扫描） | 无可用索引 / 索引选择性差 | 建或改索引；评估选择性（区分度） |
| rows 远大于实际返回 | 索引失效（函数包列/隐式转换/前导通配 LIKE） | 改写去掉失效条件 |
| Using temporary + filesort | ORDER BY/GROUP BY 无索引支撑 | 覆盖索引或改写 |
| 大表驱动小表顺序颠倒 | 统计信息过期 | ANALYZE TABLE，必要时 STRAIGHT_JOIN |

## 硬性规则

1. 建议加索引必须同时说明代价（写放大、空间）与回滚方式（DROP INDEX）；
2. 分页深翻页（LIMIT 100000, 20）优先建议游标分页（WHERE id > ?）而不是 FORCE INDEX；
3. 禁止建议「加缓存解决慢查询」——那是掩盖不是修复；
4. 数字（前后耗时/行数）写「实测口径」，没有实测就写占位。

## 常见错误

先读 `references/pitfalls.md`。特别注意：联合索引顺序建议只说「加索引」不说列顺序、
隐式类型转换（字符串列用数字比较）导致的静默全表扫描。
