# 公文写作

公文的价值在格式规范：让收文方一眼看清「谁发的、要办什么、怎么办」。

## 工作流程

1. 先选文种（见下表），文种错了全文作废；
2. 按「标题 → 主送机关 → 正文 → 落款」组织结构；
3. 正文三段式：缘由（为什么发）→ 事项（办什么事、怎么办）→ 结语；
4. 交付前对照「硬性规则」逐条自检，特别是文种与结语是否匹配。

## 文种选择

| 文种 | 什么时候用 | 规范结语 |
|---|---|---|
| 通知 | 要求知晓或执行（发规范、布置工作、转发文件） | 特此通知。 |
| 请示 | 需要上级**批准**的事项，**一文一事** | 妥否，请批示。 |
| 报告 | 向上级汇报工作、反映情况，**不需要批复** | 特此报告。 |
| 会议纪要 | 记录议定事项与分工 | （无固定结语，末尾可加"请各单位遵照执行"） |

## 输出结构

```markdown
<关于 XX 的 XX>            ← 标题 = 事由 + 文种，如「关于采购测试服务器的请示」

<主送机关>：               ← 一个主送机关；多头主送是格式硬伤

<缘由段>：一句话讲清背景与依据。
<事项段>：具体内容，分条列出；请示写清数量、预算、时间三个要素。
<结语>：按文种对照表。

<发文单位>
<成文日期>                 ← 用阿拉伯数字，如 2026年11月5日
```

## 硬性规则

1. **请示与报告不得混用**：「关于 XX 的请示报告」是错误文种——要批复用请示，不要批复用报告；
2. 请示必须一文一事：多件事写多份请示，混在一份里批复无法针对；
3. 请示的主送机关只有一个；不得同时抄送下级机关（请示是上行文）；
4. 结语必须与文种匹配，用对照表里的规范写法，不自创；
5. 标题不含标点（书名号、引号除外）；事由用「关于……的」结构；
6. 数字除成文日期外按语境使用；金额写明币种与大写（重要事项）；
7. 语气平实克制，不用形容词堆砌，不用「衷心感谢」「恳请大力支持」式的客套话开头。

先读 `references/pitfalls.md`。特别注意：把「报告」当万能文种、
缘由段写成背景长文、事项段只有标题没有可执行细节。
