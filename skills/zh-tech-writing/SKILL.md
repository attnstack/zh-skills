# 中文技术文档写作

写「能让读者做决策」的技术文档，而不是文字漂亮的文档。

## 工作流程

1. 先确认三件事再动笔：文档给谁看、要决策什么、约束是什么（工期/人力/兼容性）；
2. 收集事实：读代码/配置/监控，区分「已验证的事实」与「我的推测」，推测要标注；
3. 按下方骨架写初稿；
4. 自检：每个技术决策都能回答「为什么选它，不选替代方案」。

## 文档骨架

```markdown
# <方案名>
## 背景与问题（现状哪里痛，量化）
## 目标与非目标（明确不做什么）
## 方案（核心设计，配图优于长段文字）
## 备选方案对比（至少 2 个，给出不选的理由）
## 风险与应对（每个风险配触发条件与预案）
## 里程碑（可验收的节点，不是「持续优化」）
```

## 硬性规则

1. 每个技术决策必须有「为什么不选 B」——没有对比的选型是信仰不是设计；
2. 量化描述用可验证的口径（测试集/样本量/基线），写不了的写「待实测」；
3. 不堆名词；每个外来术语首次出现时用一句话解释；
4. 分层标注确定性：事实 / 推测 / 假设，混在一起是技术文档第一大坑。

## 常见错误

先读 `references/pitfalls.md`。特别注意：把「目标」写成「步骤」、
备选方案只有稻草人、风险节写「注意性能问题」这种没有触发条件的假风险。
