# 网关请求级限流方案

## 背景与问题

高峰期下游服务 P99 延迟超过 2s（近 7 天 3 次告警，监控面板见附录），根因是突发流量无入口节流。当前网关只做路由转发，无限流能力。

## 目标与非目标

- 目标：高峰期下游过载告警降为 0；单实例限流决策耗时 < 1ms。
- 非目标：不做分布式精确限流（见备选方案对比）；不做用户级配额管理。

## 方案

网关内存中维护令牌桶（每路由独立），阈值经配置中心热更新。超限请求返回 429 并带 `Retry-After`。
令牌桶状态仅在单实例内有效，配合负载均衡的均匀分发近似全局限流——用有损的近似换掉一个新中间件的运维成本。

## 备选方案对比

| 方案 | 优点 | 不选的原因 |
|---|---|---|
| Redis + Lua 分布式限流 | 精确全局 | 引入新依赖与 1-2ms 网络往返，两周工期风险高；当前 QPS 下单机近似已够 |
| 下游自行扩容 | 零开发 | 只是把成本转移，不解决突发流量入口问题 |

## 风险与应对

- 流量在实例间不均匀时，单机限流会误伤或漏放：触发条件为实例间 QPS 方差 > 30%；预案为切换 Redis 方案（已留接口）。

## 里程碑

1. 第 1 周：令牌桶实现 + 单测（含突发流量边界用例）；
2. 第 2 周：灰度 10% → 全量，观察一周告警面板后关闭项目。
