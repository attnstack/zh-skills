# 错误日志分析

输出的不是「这段日志说了什么」，而是「下一步查什么、按什么顺序」。

## 工作流程

1. 提取四要素：错误类型、首次出现时间线、影响面（多少请求/用户）、最近变更（发版/配置/依赖升级）；
2. 堆栈自底向上读：最靠近业务代码的第一帧是入口，最底层框架帧通常是信号而非根因；
3. 按假设排序：每个假设给出「验证成本 × 命中概率」，从性价比最高的查起；
4. 输出排查清单（有序），标注每步的预期证据。

## 分析要点

| 日志特征 | 优先假设 | 验证动作 |
|---|---|---|
| `ECONNREFUSED` 集中出现 | 下游未起/端口错 | 直接 curl 下游健康检查 |
| `ETIMEDOUT` + 长尾 | 连接池耗尽/下游限流 | 查连接池水位与下游限流计数 |
| OOM heap out of memory | 大对象聚合/泄漏 | 查 heap snapshot 对比（两次间隔取 diff） |
| 偶发且与请求无关 | 定时任务/缓存过期风暴 | 对齐首次出现时间与 cron 表 |
| 上线后才开始 | 变更引入 | 回滚是最快的验证，别先深挖代码 |

## 硬性规则

1. 不把单条日志当结论——先看聚合（频率、分布、时间相关性）再下判断；
2. 每个结论标注确定性：确认 / 高度怀疑 / 待排除；
3. 时间线必须统一时区——「时区不一致导致误判」本身是高频根因；
4. 敏感信息（token/手机号）在输出里脱敏，原文不外传。
