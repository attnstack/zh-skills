A collection of Chinese-language skills for coding agents (Claude Code, Cursor, etc.), plus an installer CLI. One command installs 14 Chinese workflow skills — weekly reports, code review, design docs, typography normalization, incident postmortems, official document writing — and it seriously solves two pain points: installing skills on Windows without admin rights, and verifying that a skill description actually triggers before you ship it.

## Try it


## Quick start

```bash
npx zh-skills add --all                        # install everything to detected agents
npx zh-skills add zh-typography --agent claude-code
npx zh-skills add --route "写周报"              # describe your need; router picks top 3
npx zh-skills doctor                           # environment check
```

Installs from npm in seconds. Prefer GitHub? `npx github:attnstack/zh-skills add --all` (first run clones and builds, about a minute). After installing, just ask your agent in Chinese — "帮我写周报", "校对这段文档的排版" — and the matching skill triggers.

## What's inside

14 skills, each a folder with `SKILL.md` (main instructions), `examples/` (verifiable input/output pairs) and `references/pitfalls.md` (real failure cases):

zh-tech-writing (design docs) · zh-pr-description · zh-readme-gen · zh-api-doc · zh-sql-optimization · zh-code-review · zh-typography · zh-test-case-gen · zh-log-analysis · zh-weekly-report · zh-commit-message · zh-requirement-breakdown · zh-postmortem (incident postmortems) · zh-gongwen (official document writing)

Four ship executable check scripts (typography, commit message, PR description, postmortem structure) — whether output passes the spec is decided by a script, not by vibes. zh-typography's example output.md is generated by `fix.mjs` and diffed line-by-line in CI.

## Design decisions

**Descriptions are written as "when to use + when NOT to use", and the router penalizes the negative text separately.** Whether a skill triggers depends almost entirely on its description. Writing only the positive side is not enough: a writing skill whose description says "not for marketing copy" will actually get routed marketing-copy queries, because full-text search matches the exclusion text as a trigger. So every description must carry a "不适用于" (not for) section, and the router subtracts a full idf-weighted score for negative hits. This bug was caught by tests, not invented.

**Character bigrams + BM25, no models.** At a dozen documents, brute-force scoring takes ~0.05ms — bolting on a 30MB embedding model would be absurd, and Chinese word segmenters ship dictionaries. The n-gram size is measured, not guessed: unigrams (n=1) produce an 84.2% false-positive rate on negative samples; trigrams (n=3) are too sparse for short queries at 64.8% hit rate; bigrams win on both.

**symlink → junction → copy fallback on Windows.** Creating symlinks on Windows needs admin rights or Developer Mode — not available under npx. Order: plain symlink on Unix; junction first on Windows (NTFS reparse point, no privilege needed, directories only, absolute target required), then copy. The actual mode is recorded in a manifest; `update` uses it to pick semantics — links follow the source, copies need version comparison.

**The platform triggers installed skills natively; the CLI `route` command exists for tuning descriptions.** Run `route "<how a user would ask>"` and see immediately which skill matches and why, without trial-and-error inside an agent. Those 73 labeled queries are also the CI regression: any description change must pass.

**Misroutes are recorded, and fixes are verified with data.** When routing goes wrong in daily use, `route "<query>" --label <expected-skill>` records it; after tuning, `feedback` replays the history against the current router and reports the hit-rate delta. Skill authors can lint their own folders with the same checks the repo CI uses: `npx zh-skills lint <dir>`.

## Benchmark

Setup: test set is `tests/router/queries.jsonl` (54 positive = 26 direct + 28 paraphrased, 19 negative that must trigger nothing); baseline is no routing, all 14 skills injected; results are deterministic. Latency measured locally (Windows 11 / Node 24) — run `npm run bench` for your own machine.

| cjkN | negative penalty | Top-1 | Top-3 | negative FP rate |
|---|---|---|---|---|
| 1 | 0 | 96.3% | 100.0% | 84.2% |
| 1 | 1.0 | 94.4% | 100.0% | 84.2% |
| 2 (default) | 1.0 | 96.3% | 100.0% | 0.0% |
| 2 | 0 | 98.1% | 100.0% | 0.0% |
| 3 | 0 | 63.0% | 64.8% | 0.0% |

Single route call: mean ~0.06ms / p99 ~0.2ms (1000 samples). Context: top-3 injection averages 3,027 bytes vs 28,959 bytes full injection — 89.5% saved.

Two honest notes: the negative penalty costs 1.8pp of Top-1 (one query), kept because exclusion-scenario false positives hurt user trust more; hit rates reflect lexical matching — paraphrase tolerance is limited, see limitations.

## Tests

```bash
npm test                 # 70 tests: unit + router regression + e2e install + typography script + CLI smoke
npm run validate:skills  # skill asset gate: schema / examples / script consistency
npm run bench            # hit-rate matrix + latency + context, writes bench/results.json
```

CI runs on ubuntu / windows / macos. Regression gates: Top-3 ≥ 85%, negative FP ≤ 10%.

## Known limitations

- Lexical routing: paraphrases only hit if the test set happens to contain that phrasing. Embeddings would fix it, but at this scale they are not worth the install size; planned as optional in v0.3.
- codex / opencode / gemini-cli skill directories follow community conventions, not version-checked official docs — marked experimental; `--target <dir>` always works.
- The eval set is labeled by the author (self-circularity risk); negative samples and per-kind reporting mitigate it a little. A third-party labeled set is still missing.
- `learn` appends to the installed copy, which npx upgrades wipe — lasting fixes come from PRs back to this repo.

## Roadmap
